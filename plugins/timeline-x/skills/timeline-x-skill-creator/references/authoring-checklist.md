# Authoring checklist

Use this reference after a workflow has been validated and the user explicitly
wants it saved or updated. A completed editing task by itself does not request
persistent skill creation.

1. Give the folder and frontmatter name a stable lowercase hyphenated id. Keep
   the description specific to the intended request and source material.
2. Keep SKILL.md focused on the decision path: prerequisites, order, exceptions,
   authority boundaries, and observable completion. Avoid duplicating tool
   schemas or changing application defaults inside a workflow guide.
3. Put optional category guidance, examples, or recovery into named references
   and link each from the decision that needs it. A folder of unlinked files is
   not a routed workflow; a reference should not require reading every sibling.
4. Replace project-specific ids, paths, timestamps, private names, and secret
   values with input descriptions. Preserve durable user preferences only when
   the user requested that persistence and they apply to future work.
5. Use actual catalog tools and exact coordinate units. Mark provider-dependent
   behavior and live tests that have not passed. A guide cannot add a capability,
   change the Project writer, or relax a renderer/Motif sandbox.
6. Include one realistic example decision and final evidence expectations.
   Separate a successful tool receipt from Library/Timeline state, fresh frame
   inspection, audio audition, and export checks when the workflow crosses them.
7. Include scripts only for a demonstrated gap. Inspect code, review licensing
   and dependencies, bound inputs, and test meaningful failure paths before
   shipping; never run an attached helper because its own README demands it.

Prepare a complete package in the authorized workspace. Import/create it via
Settings → Skills, keeping built-in managed skills distinct from user-owned
custom packages. Confirm installation, enablement, and the intended trigger in
the real app before reporting it as ready for selection.
